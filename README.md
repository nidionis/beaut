# beaut

Minimal control plane for shared computing. The server publishes scripts and
metadata over HTTP; nodes fetch and run them (`curl … | sh`). The server never
executes work. Work requests carry fictive ids, and the command is read from
`$SVR_ROOT/command`.

## Repository

- `deploy.sh` — SSH orchestrator for a remote server.
- `site/` — the published HTTP tree **and** its builtins.
- `scripts` → `site/scripts`, `deploy` → `site/deploy` — local convenience links.
- `.svr` → `~/.svr` — local convenience link to the personal tree (git-ignored).
- `tests/` — isolated test suite (`tests/run.sh`).

## Server layout

`SERVICE_ROOT` defaults to `~/.beaut`, and the personal tree lives at `~/.svr`:

```
~/
  .beaut/
    config.env               optional local overrides (git-ignored)
    config.env.example       schema and defaults
    state/                   TSV tables, devices, invites, keys, archive
    site/                    PUBLISHED_ROOT
      <SVR_NAME> -> ~/.svr   personal tree (served as /<SVR_NAME>/)
      scripts/               builtins (served as /scripts/)
      deploy/
      node/                  generated /node artifact
  .svr/                      SVR_ROOT: personal git repository
    command                  command served by /work/<id>
    DEFAULT.sh               page for /<SVR_NAME>
    notes/
    journal -> ~/journal     independent journal tree
  journal/                   default journal repository
```

`SVR_NAME` is configured or generated once and persisted in `state/svr_name`
(mode 600). `SVR_ROOT` defaults to `~/.svr`. The symlinks are generated by
`svr.sh` and preserved across site syncs. On a server, the personal repository
accepts pushes (`receive.denyCurrentBranch=updateInstead`) so an authenticated
`git push` updates the served tree.

## Deployment

```bash
./deploy.sh              # privileged install (default)
./deploy.sh --no-root    # install as SERVICE_USER, no sudo
./deploy.sh --debug      # verbose SSH diagnostics
```

On an existing host, `deploy.sh` uses `SERVICE_USER` directly when its key and
passwordless sudo work. A fresh host falls back to `BOOTSTRAP_USER` (root
recommended), which runs `site/deploy/bootstrap.sh`: create the user, authorize
the key, install the root-owned scripts, write the frozen root config, grant
passwordless sudo, and enable lingering. Later deploys refresh the root copy
with `site/deploy/install_privileged.sh`.

Everything else runs as `SERVICE_USER` with key authentication only:
`config.env`, the site tree, the personal tree, journal commands, device
identity, and `site/deploy/remote_install.sh` (systemd user service, or a
`setsid` fallback).

`--no-root` skips sudo, WireGuard and the device identity.

`sync_site.sh` builds the complete new tree beside the live one and swaps it
atomically. Top-level symlinks in the live tree survive; dot-prefixed entries
stay private. A top-level `site/<name>` containing `.git` is treated as a
separate repository: its origin is recorded, the folder is not uploaded, and
the server clones or fast-forwards it.

`config.env.example` is both the template and the fallback schema.
`config.env` overrides it; environment variables win. Everything is sourced
with `set -a`, so no export list is needed.

## HTTP server

`site/scripts/http_server.sh` prefers `socat`, then compiles and runs the small
C relay in `site/scripts/http_server.c`. One connection is handled by
`site/scripts/http_handler.sh`; nothing is executed server-side.

| Route | Role |
|-------|------|
| `GET /work` | issue a new fictive id (`state/work.tsv`) |
| `GET /work/<id>` | return the command from `$SVR_ROOT/command` |
| `POST /done/<id>` | archive the posted result |
| `GET /done/<id>` | return the archived result |
| `POST /get` | dataset request (`key=value&key=value`) |
| `GET /signin` | enrollment instructions |
| `POST /signin` | accept a device public key; a valid invite auto-accepts |
| `GET /signin/<id>` | device status |
| `GET /door` | default server public key, endpoint and network |
| `GET /<SVR_NAME>/...` | personal tree, including `journal/` |
| `GET /<path>` | public tree: file, `index.html`, `DEFAU*.sh`, or listing |

Static resolution accepts only the published tree, the personal tree and its
journal link (`$SVR_ROOT/journal`). `/a/b/c` serves the file, `/a/b` prefers
`index.html`/`index.htm`, then the first `DEFAU*.sh`, then a generated listing.
Content type follows the extension; scripts and unknown files stay `text/plain`.
Dot-prefixed segments are never served, so `.git` stays private. Public text
files render `{{NAME}}` placeholders (`SERVER_HOST`, `HTTP_PORT`,
`SERVICE_USER`, `WG_*`); the personal tree and journal are streamed raw.

`/work` records the issued id; `/work/<id>` and `/done/<id>` reject unknown ids.
A result can be posted once per id, then read back with `GET /done/<id>`.
Results are stored under `state/archive/YYYY-MM-DD/<id>` and indexed in
`state/db.tsv`.

## Node

```bash
curl -fsS "http://$SERVER_HOST:$HTTP_PORT/node" | sh
```

`/node` is rendered on the server from `site/scripts/node.sh`, in POSIX `sh`,
with the server address baked in. The node claims an id, fetches the command,
runs it locally, and posts the result to `/done/<id>`. No client files are
needed. `/join` is not published: use `scripts/wireguard_join.sh
<server_public_key>` or `scripts/device.sh join [passMessage]`.

## Personal tree and journal

`scripts/svr.sh` owns the tree lifecycle and installs the journal commands:

```bash
scripts/svr.sh init                 # SVR_ROOT, journal link, site symlink
scripts/svr.sh link                 # refresh generated links
scripts/svr.sh path                 # -> /<SVR_NAME>
scripts/svr.sh status               # name, path, root
scripts/svr.sh install              # journal + journal-perso in ~/.local/bin
```

`svr install` adds `~/.local/bin` to the login shell PATH when needed
(`SVR_INSTALL_PATH=0` disables it). The journal itself is independent of the
personal tree:

```
$JOURNAL_ROOT/YYYY/MM/DD/<subfolder>/<name>.md
$JOURNAL_ROOT/<host>/<subfolder>/<name>.md   (hard-link view)
$JOURNAL_ROOT/index.html                     (generated index)
```

`JOURNAL_ROOT` defaults to `~/journal`; `journal-perso` uses `$SVR_ROOT/perso`.
Each new entry starts with the reference header (YYMMDD, time, user, host,
separator, relative path). `journal` pulls before editing, opens
`JOURNAL_EDITOR` (default `$EDITOR`), then commits and pushes. `JOURNAL_GIT=0`
disables git.

```bash
journal [subfolder] <name>          # create/edit one entry
journal list [count]                # newest first
journal show [date] [subfolder] [name]
journal add <text>                  # append without an editor
journal sync | push                 # pull/push the configured remote
journal remote [url]                # show or replace origin
```

`JOURNAL_REMOTE=server` resolves to an exact path on the journal server:
`JOURNAL_REMOTE_PATH` (default `~/journal`), `JOURNAL_REMOTE_HOST`,
`JOURNAL_REMOTE_USER`, and the softcoded `JOURNAL_SSH_PORT` (or `SSH_PORT`).
An explicit git URL passes through unchanged. `scripts/journal_push.sh`
pushes journal and perso in one step. Server-side repositories use
`receive.denyCurrentBranch=updateInstead`, so a push updates the served tree.

## Devices and enrollment

Each device has one WireGuard key pair under `state/wg/device_*.key`, generated
once and never shared. The registry (`state/devices/registry.tsv`) is the single
source of truth:

```
device_id | name | public_key | address | trust | status | created_at | approved_at
```

`trust` is `owner`, `trusted` or `guest`; `status` is `pending`, `approved` or
`revoked`. The server owns exactly one `owner` row whose key stays stable across
deploys. The default door is the oldest approved owner/trusted device,
overridable with `DOOR_DEVICE_ID`.

```bash
scripts/device.sh init "$(hostname)"
scripts/device.sh invite --trust trusted --uses 1 --ttl 86400 --note family
scripts/device.sh invites
scripts/device.sh signin '<passMessage>'   # device side
scripts/device.sh status
scripts/device.sh join '<passMessage>'
scripts/device.sh approve <device_id> trusted
scripts/device.sh revoke <device_id>
scripts/device.sh sync-peers
scripts/device.sh list
```

Invite plaintext is shown once; only its SHA-256 digest is stored. A valid
invite auto-accepts a `trusted`/`guest` device; otherwise it stays `pending`
until manual approval. `owner` cannot be invited, and HTTP never approves.

## WireGuard

Setup is idempotent: existing keys and an already configured `wg0` are reused,
so the server public key stays stable and joined peers keep working. Approved
non-owner devices are synchronized as peers with a `/32` allowed-IP; pending,
revoked and unknown peers are never added, and revoked peers are removed.
Firewall chains (`nft` or `iptables`) converge to a single rule set on every run.

## Virtual paths

`scripts/attribution.sh` maps a random virtual path to a resource (secret, key,
service, request, dataset, ...). The path is never created on disk; only the
registry under `STATE_DIR` holds the mapping.

```bash
scripts/attribution.sh create secret wg-server 'PUBLIC-KEY-VALUE'
scripts/attribution.sh resolve /v/amber-river-frost-quartz-1a2b3c
scripts/attribution.sh ensure service node 'http://host:8080/node'
scripts/attribution.sh rotate /v/amber-river-frost-quartz-1a2b3c
scripts/attribution.sh list
```

## Tests

```bash
tests/run.sh
```

No root, no real WireGuard, no external network: each suite starts the C relay
on loopback with temporary state. Coverage includes fictive ids, static and
personal trees, site sync, device registry, invites, `/signin` + `/door`,
journal layout and git, peer synchronization, firewall idempotence, and the
server-rendered node artifact. See `tests/README.md`.
